# Blind investigation, then delta

## Define and disclose the boundary before reading project context
A blind audit means no prior assessment conclusions are used to select or validate findings. It does not mean the current code/tests have no traces of earlier fixes. Do not claim absolute blindness, exhaustive coverage or proof that fixes are correct simply because tests pass.

Follow required system/user/repository instructions. For this workflow, the kit's normal PROJECT/MAP/PROGRESS/board/bootstrap loading is deferred until after freeze. Never bypass mandatory instructions; if required instructions or automatically loaded memory already contain prior findings, disclose that exposure before investigation. A prompt cannot erase context already read.

Before proceeding, record a contamination ledger: prior report exposure; PROJECT/MAP/PROGRESS/board/issue summaries; conversation history; auto-loaded memory/instructions; commit messages/diffs; test names/comments that disclose prior findings. Record paths/categories and timing without copying finding details into worker prompts. Classify the run as `no known prior-assessment exposure`, `fresh workers; coordinator exposed`, or `contaminated/not blind`. Never downgrade exposure after a fresh prompt in the same context.

If strict blindness was requested and the investigator is already exposed, use genuinely fresh native contexts without inherited transcript, if supported and permitted. Pass only this protocol, required instructions, a neutral task, the pinned source state and bounded subsystem paths derived from manifests/source topology. An exposed coordinator must not steer workers using prior conclusions. If fresh contexts cannot be established, stop before substantive investigation and ask for a new session; offer a clearly labeled non-blind audit as an alternative. Do not launch nested CLIs, disable policy, or remove instruction files to manufacture a clean context.

## Before freeze: permitted inputs
- Read required operating instructions and the current skill's generic references. Prefer manifests, build configuration, current application code/tests and runtime evidence.
- Defer every prior report and archive (case-insensitive naming), PROJECT.md, MAP.md, PROGRESS.md, generated codebase maps, board databases/tickets, audit/remediation notes, issue/PR discussion, chat history retrieval, session logs and kit backup/retired/incoming copies. The rule covers content, not just these filenames. If a source comment/test or required instruction reveals an earlier finding, log that exposure and limit the blindness claim.
- Do not run Git log/blame/show, commit-message searches, fix-cluster/churn prioritization, global repository text search, or tooling that summarizes earlier audit outcomes. Source revision/status commands are allowed; defer history-based investigation to the delta phase. Build a fresh map from source instead of loading a generated one.
- Run `scripts/repo-recon.sh` for source-only recon. It excludes known context/config/artifact paths and documentation and does not run history scans. It is a convenience filter, not a confidentiality boundary. Review explicit source roots before further `rg`/tool reads. Do not assume a renamed report or model memory is filtered automatically.
- Workers receive neutral scope and raw current evidence, not old finding IDs, six-fix summaries, previous risk rankings or author confidence. No full-parent transcript inheritance for an independence claim. Validators receive the new candidates and raw source/repro evidence only. If fresh contexts are unavailable, do not label same-context validation independent.

## Freeze before opening prior material
1. Run `python3 scripts/audit-guard.py begin --root <project>` using the actual skill script path. This copies the existing report without displaying it, detects both AUDIT_REPORT.md and audit_report.md, snapshots protected-file hashes, and prints a unique session directory. Never move/delete skills, source, context files or the old report for isolation.
2. Write the independent report to `<session>/draft.md`. Include coverage, verification gaps and the contamination ledger. Do not claim a delta yet. Preserve the existing report.
3. Run `python3 scripts/audit-guard.py freeze --root <project> --session <session> --draft <session>/draft.md`. If integrity checks fail, stop and investigate. Do not conceal deletion by reinstalling or restoring automatically. The frozen report and its SHA-256 remain evidence of the pre-delta findings.
4. Only after successful freeze, read `<session>/previous-report.md` if it exists and the deferred context/history needed for comparison. Write `<session>/delta.md` separately. Match by root cause, not ID alone. For each old finding use `independently rediscovered`, `still reproducible (delta-only)`, `fix present in source; verification limited`, `verified resolved within stated checks`, or `not assessed/insufficient evidence`. Cite actual source and commands. A post-freeze discovery belongs to the delta, not the frozen independent findings. Never use absence from the new report as proof of resolution.
5. Publish with `python3 scripts/audit-guard.py publish --root <project> --session <session> --delta <session>/delta.md` (omit --delta only if no previous audit exists). This preserves the frozen findings and appends the comparison, checks protected paths, and atomically replaces only the chosen report. Do not clean up the evidence directory.

The helper detects changes at checkpoints; it cannot prevent arbitrary agent/tool writes or guarantee context isolation. Audit mode authorizes report/evidence writes only. Never run kit setup/sync/merge/retirement, remediation, `git clean`, broad checkout/reset, or delete/move/edit `.agents`, `.codex`, `.claude`, skill directories or project instructions during the audit. Dead-code and skill-removal recommendations are report text, never actions. Any explicit later kit cleanup is a separate task.
